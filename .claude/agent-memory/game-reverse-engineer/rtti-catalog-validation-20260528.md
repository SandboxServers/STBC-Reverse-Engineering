# rtti-class-catalog.md V5 Validation (2026-05-28)

## Validation outcome
Foundation claims (MSVC RTTI count, NiRTTI hash table, totals) validate cleanly. The per-class
catalog has a SYSTEMATIC ISSUE in the TG section: rows citing addresses in the 0x0091xxxx
range point INTO the middle of SWIG `_p_ClassName\0` pointer-type strings (the bare class
name appears as a substring 3 bytes in). The bare class name strings actually live in either
.rdata (0x008Dxxxx-0x008Exxxx) or .data (0x0095xxxx) ranges. The NI section and game-specific
section are correctly anchored on bare class strings.

## Key MCP techniques

### Counting NiRTTI factory registrations precisely
```
get_xrefs_to(0x009a2b98) -> 237 total xrefs
  117 functions with [READ + WRITE] = registration functions
  2 functions with [READ only] = consumers (FUN_008176b0=NiStream_LoadObject, FUN_00818150)
  1 standalone READ at 0x00816c40 (no containing function = stray bytes consumer)
Result: 117 registrations EXACTLY matches doc. NOT 118 (the snapshot's (237-1)/2 calc).
```

### NiRTTI hash table structure (verified via decompile of NiNode registration at 0x007e3670)
- Bucket count: 0x25 = 37
- Bucket array allocated at construct time: 0x94 = 148 bytes (= 37 * 4-byte ptrs)
- Table struct size: 0x10 bytes
  - +0x00 = vtable ptr (= PTR_FUN_0088b7c4 after init, PTR_LAB_0088b7d8 during init)
  - +0x04 = entry count
  - +0x08 = bucket count (37)
  - +0x0c = bucket array ptr
- Hash node: 0x0C bytes (className ptr, factory ptr, next ptr)
- Lazy init: guard flag at DAT_009a18a0 (per-class) prevents re-registration
- Vtable at 0x0088b7c4: 8 function pointers including hash(+0x4), strcmp(+0x8), insertNode(+0xc)

### Distinguishing bare-class-strings from SWIG-ptr-type-strings
Pattern: a SWIG pointer-type string is `_p_TGFoo\0`. If you search by `^TGFoo$` (regex
anchor), Ghidra returns only the bare string. If you search by `TGFoo` (substring), you also
get matches inside `_p_TGFoo` strings — and the substring address is `_p_TGFoo_addr + 3`.

The TG section of rtti-class-catalog.md has many rows citing addresses ending in `B3`, `7F`,
`4B`, `EE3`, etc. — these are all `(SWIG_ptr_string_base + 3)` offsets, meaning the row was
generated by scanning for the substring "TGFoo" rather than the bare class name.

**To re-derive correct addresses**: for each "wrong" 0x0091xxxx row, search for `^ClassName$`
in Ghidra strings — the result is the canonical bare string. E.g.:
- doc: TGObject @ 0x009142B3 → actual bare: 0x0095b05c
- doc: TGUIObject @ 0x0091444B → actual bare: 0x0095cf90
- doc: TGAction @ 0x00913EE3 → actual bare: 0x0095b874
- doc: TGAnimAction @ 0x00913EE3 → actual bare: 0x0095b758 (these were not duplicates — they're 2 distinct classes but doc cited the same intermediate-substring address for both)

### SWIG method-count caveat
The doc's "SWIG Methods: 94" for TGUIObject etc. = count of `^ClassName_` strings in binary.
But these include enum constants (TGSound_SS_*, TGSound_LS_*, TGUIObject_ALIGN_*, etc.) —
not just methods. Actual callable method count is generally 4-10 less than the doc number.
For triangulation purposes the doc's count is "Python-binding identifier count" not strict
"method count". This is across all 32 SWIG rows.

## Address-range claim correction needed
Doc says "TG class strings distributed across .rdata (0x008Dxxxx-0x008Exxxx) and .data
(0x0091xxxx-0x0095xxxx)". Per `list_segments`:
- `.rdata`: 0x00888000-0x008bafff — does NOT include 0x008Dxxxx
- `.data`: 0x008bb000-0x009b5357 — INCLUDES BOTH 0x008Dxxxx AND 0x0091xxxx-0x0095xxxx

Correction: All TG class strings are in `.data`. The 0x0091xxxx-0x0095xxxx subrange is the
SWIG pointer-typename string region; 0x008Dxxxx-0x008Exxxx and 0x0095xxxx are the bare
class-name regions.

- Not-found (no exact-match bare string): 53
- Bare-string address range observed: **0x008DBA14 – 0x0095CFA0** (one outlier `TGCondition`

- Dominant cluster: **0x00958000 – 0x0095D200** (24 of 28 confirmed names) — this is the
  primary "TG bare-class-name region" in `.data`
- Secondary cluster: **0x00932B00 – 0x00933600** (5 confirmed names — typed input/IO event

- One off-cluster: **0x008DBA14** (`TGCondition` only)

### Patterns observed
1. **The "Managers" category is largely fictional.** Only two real TG*Manager class strings
   exist in the binary: `TGActionManager` (0x0095b71c) and `TGSoundManager` (0x0095ba70).
   The other 15 manager names listed in the catalog (TGAudioManager, TGEventManager,
   TGModuleManager, TGRenderManager, TGSystemManager, TGFileManager, TGTextureManager,
   TGNiManager, TGPlayManager, TGScriptManager, TGMessageManager, TGTimerManager,
   TGGameManager, TGControlManager, TGVarManager) have NO corresponding bare-string and
   appear to be speculative additions. **Recommendation: docwriter should DROP these rows
   from the catalog entirely**, not flag them `confidence: low`.

2. **The Network Messages category is entirely speculative.** None of TGMessage,
   TGAckMessage, TGBootPlayerMessage, TGConnectMessage, TGDisconnectMessage,
   TGDoNothingMessage, TGNameChangeMessage have bare-string anchors. These are real
   classes (transport-layer message factories — confirmed elsewhere in our RE work) but
   they are NOT exposed via SWIG/Python and therefore have no bare-string in the SWIG
   string region. Their RTTI lives in vtable plate-comments and factory tables only.
   **Recommendation: docwriter should either drop these from the SWIG/RTTI catalog or
   move them to a separate "Internal C++ classes (no SWIG binding)" section sourced from
   factory ID 0x0100-0x010D tables.**

3. **Networking core classes (TGWinsockNetwork, TGNetGroup, TGNetPlayer, TGPlayerList,
   TGGroupPlayer, TGEncrypt) are also not in the bare-string set.** Only `TGNetwork` has
   a bare string (at 0x0095aa14). The others are internal C++ classes with no Python
   bindings.

4. **Math/Data Type classes (TGColorA, TGMatrix3, TGRect, TGStringStream, TGTypeInfo) are
   not in the bare-string set.** These are likely value-types or POD structs that the
   game's RE history has assumed exist by analogy with NiColorA/NiMatrix3/NiRect but
   which were never given SWIG bindings (or never existed as separate classes in this
   build of the engine).

5. **UI Framework: 6 of 18 names are real.** Confirmed: TGUIObject, TGFrame, TGPane,
   TGButton, TGTextButton, TGDialogWindow. The other 12 (TGCheckButton, TGRadioButton,
   TGScrollBar, TGTextBox, TGLabel, TGListBox, TGComboBox, TGSlider, TGSpinner, TGImage,
   TGProgressBar, TGTab) do not exist as bare-string class names. Per the broader UI
   search, the real UI widget classes that DO exist include TGButtonBase, TGTextButton,
   TGStringDialog, TGConsole, TGPrompt, TGIcon, TGIconGroup, TGRootPane, TGFontGroup,
   TGFrameWindow.

### Range claim update for the catalog
Replace the doc's TG-section address-range claim with:
> TG bare class-name strings live in two `.data` sub-regions:
> - **Primary**: 0x008D8000 – 0x008E6000 (early `.data`, ~18 classes)
> - **Secondary** (the "TG SWIG class string table"): 0x00958000 – 0x0095D200 (~47 classes)
> - **Outlier**: typed input-event classes at 0x00932B00 – 0x00933600 (5 classes)
>
> The 0x0091xxxx – 0x00945xxx range cited in earlier doc revisions points into SWIG
> pointer-type strings (`_p_TGFoo\0`); those substring offsets are NOT canonical
> bare-string anchors and must not be cited.
